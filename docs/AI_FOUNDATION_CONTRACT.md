## 7. OpenAI key status — stated plainly

The **code** is fully wired: `defineSecret("OPENAI_API_KEY")` is declared and bound to `onMessageCreate`'s
`secrets` array (`functions/ai.js:26, 47`), and the adapter reads `process.env.OPENAI_API_KEY` exactly as
Firebase Functions v2 injects a bound secret (`providers/openai/adapter.js:10`). That much is unambiguous
from source and is the current deployed code (this repo's `functions/vendor/ai-foundation` is verified
identical to `packages/ai-foundation`, §"Files read" above).

What source code **cannot** tell you: whether an actual secret *value* has been set for
`OPENAI_API_KEY` in this Firebase project's Secret Manager. That is a live infrastructure fact, not
something present in any file — per this task's own instruction, this document states "not present in
code" rather than guess. If the value has never been set (via `firebase functions:secrets:set
OPENAI_API_KEY` or equivalent), §6's graceful-degradation path is exactly what runs on every message: no
suggestions will ever fire, silently, and the app will look and behave identically to a fully-working
build except that `suggestedActions` never gets any documents. Confirming the secret's live value requires
a separate, out-of-source-scope check (e.g. `firebase functions:secrets:access OPENAI_API_KEY` against the
deployed project) — this document does not perform that check.

## 8. Security rules — exact predicates

All citations below are line numbers in `firestore.rules` as read for this extraction.

- **`messages/{messageId}`** — `firestore.rules:236-245`:
  - `allow read`: `signedIn() && isActiveMember(<parent conversation's orgId>) &&
    canAccessConversation(<parent conversation data>)` — looks up the parent conversation via
    `get(/databases/$(database)/documents/conversations/$(resource.data.conversationId))`
    (`firestore.rules:238-239`).
  - `allow create`: `signedIn() && request.resource.data.senderUid == request.auth.uid &&
    isActiveMember(<parent conversation's orgId>) && canAccessConversation(<parent conversation data>)`
    (`firestore.rules:240-243`) — note this does **not** restrict which other fields may be set (no
    `hasOnly()`/`affectedKeys()` check on create) — consistent with §2's finding that every message field
    is client-written.
  - `allow update, delete`: `if false` — unconditional, no exceptions (`firestore.rules:244`).
  - Rule comment (`firestore.rules:233-235`) explicitly notes `orgId` is *not* a field the rule checks on
    the message doc itself — tenant isolation is enforced entirely via the parent conversation lookup.

- **`suggestedActions/{actionId}`** — `firestore.rules:253-257`:
  - `allow read`: `request.auth != null && isConversationParticipant(resource.data.conversationId)`
    (`firestore.rules:255`), where `isConversationParticipant()` is
    `request.auth.uid in get(.../conversations/$(conversationId)).data.participantUids`
    (`firestore.rules:279-282`).
  - `allow write`: **`if false` — unconditional, no exceptions, no scoped status-flip carve-out**
    (`firestore.rules:256`).
  - **Discrepancy from a prior assumption**: this task's own prompt characterized the client as having "the
    scoped status flip already allowed in the Phase A rules (`.diff().affectedKeys().hasOnly([...])`)" for
    `suggestedActions`. That pattern **does exist** in this ruleset, but only for `jobListings`
    (`firestore.rules:134-139`, restricted to the `jobStatus` key) and `jobApplications`
    (`firestore.rules:157-159`, restricted to `applicantStatus`) — **not** for `suggestedActions`, which has
    no client write path of any kind. The only way a `suggestedActions` doc's `status` changes is via the
    `confirmSuggestedAction`/`dismissSuggestedAction` callables, which run under the Admin SDK and are not
    subject to Firestore Security Rules at all.
  - `ledgerEntries`/`milestones`/`snags` follow the identical pattern: `allow read` gated on
    `isConversationParticipant(resource.data.conversationId)`, `allow write: if false` unconditionally
    (`firestore.rules:260-271`).

- **`conversations/{conversationId}`** (relevant because §5 shows the AI foundation reads
  `participantOrgIds`/`participantUids` off this doc) — `firestore.rules:216-225`: `allow read` requires
  `isActiveMember(resource.data.orgId) && canAccessConversation(resource.data)`; `allow create` requires
  the creator's uid in `participantUids`, `createdBy == auth.uid`, and org-scope creation additionally
  gated to `owner`/`admin`/`manager`; `allow update` requires participancy or owner/admin, plus scope
  immutability unless the caller is owner/admin/manager.

- **`organizations/{orgId}`** (relevant because §5 shows `name`/`type` are read) —
  `firestore.rules:188-192`: `allow read: if isActiveMember(orgId)`.

- **`memberships/{membershipId}`** (relevant only to note the AI foundation never reads this collection at
  all — §5) — `firestore.rules:195-206`: read restricted to the membership's own `uid` or an
  owner/admin/manager of that org; not touched by anything in `functions/ai.js` or the vendored package.

## 9. Discrepancies vs. design docs / prior assumptions (explicit list)

1. **`suggestedActions` is a top-level collection, not `message.suggestedActions`.** Two prior chat-side
   prompts assumed the latter. Ground truth: `functions/ai.js:62` writes to
   `db.collection("suggestedActions").add(...)`, a sibling top-level collection to `messages`, referencing
   its source message only via a `messageId` field (§3).
2. **`messages` is a top-level collection, not nested under conversations/organizations.** Confirmed by the
   trigger path `"messages/{messageId}"` (`functions/ai.js:47`) and every query in the vendored package
   (e.g. `db.collection('messages').where('conversationId', '==', conversationId)` —
   `context/sources/messages.js:4-9`) — no parent path segment anywhere.
3. **The message content field is `text`, not `body`/`content`/`message`.** §2.
4. **The action taxonomy has 6 values in code, not the 5 previously assumed** — `log_approval` exists in
   `intent/taxonomy.js:7-10` and the live system prompt, but is absent from the design set this task
   listed for comparison (§4).
5. **`log_approval` has zero dedicated payload fields** in `suggestedActionPayload` — unlike the other 5
   action types, it carries no structured data at all if ever emitted (§4).
6. **Only 3 of the 6 action types can be confirmed into real data** (`log_ledger_entry`, `set_milestone`,
   `flag_snag`); the other 3 (`tag_project`, `share_reference`, `log_approval`) will schema-validate fine
   out of the classifier but hard-fail at `confirmSuggestedAction` time with `failed-precondition` (§4).
7. **`suggestedActions` has no client write path whatsoever** — `allow write: if false` unconditionally
   (`firestore.rules:256`). There is no scoped `.diff().affectedKeys().hasOnly([...])` status-flip rule for
   this collection (that pattern exists elsewhere in the ruleset, for `jobListings`/`jobApplications`, but
   not here) — §8.
8. **`memberships` is never read by the AI foundation.** Participant "roles" used in the AI context are a
   hard-coded `'member'` placeholder for every participant uid, not a real lookup against the `memberships`
   collection (§5).
9. **`conversation.orgId`/`scope`/`teamId`/`createdBy`/`linkedEntities` are never read** by the AI
   foundation — only `participantOrgIds` and `participantUids` are (§5). The `orgId` written onto a
   `suggestedActions` doc comes from the **message's** `senderOrgId`, not the conversation's `orgId` field.
10. **`explanation` on a `suggestedActions` doc is a structured object**
    (`{ reasoning, evidence, confidence, recommendedAction }`), not a plain string (§3, §6 via
    `explainability/attach.js`).
11. **`context/sources/projectMeta.js` is present but fully dead code** — not imported by `builder.js`, not
    referenced by any `contextRequirements` array in the one deployed prompt template (§5).
12. **Whether the OpenAI secret's live value is actually set is not determinable from source** — the code
    wiring is complete and deployed, but that is a distinct fact from whether suggestions will actually
    fire (§7).
